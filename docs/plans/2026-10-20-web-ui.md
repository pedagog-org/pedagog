# Web UI

## Rationale

Everything works through `hammer` today; a web UI lets students submit and read
results, and staff run a course, without a terminal (and lets us try the platform
hands-on before workspace sessions). The screens are specified in
`docs/design/web-ui-brief.md`; Claude Design is producing the visual design. This plan
starts with a bare skeleton so the build, dev loop and CI exist when the designs land.

## Decisions (2026-10-20)

- **Client-side rendering (CSR):** the `web` crate is a Leptos app compiled to
  WebAssembly, built with `trunk` into static files (`index.html`, the `.wasm`, CSS),
  calling the REST api. Chosen over SSR (inside the api or as its own service) for the
  least to build and run; the cost is a blank page until the WASM loads (~0.5–1 s).
- **Same host:** the UI at `/`, the api under `/api` (same-origin cookies, no CORS, one
  certificate). Moving the api under `/api` is a later step (hammer follows it).
- **Dependencies (approved):** `leptos` 0.8 (`csr`), `console_error_panic_hook` 0.1,
  `gloo-net` 0.7 (HTTP from the browser); later `leptos_router` 0.8 and `leptos_meta`
  0.8 when there are pages. Build tool `trunk` 0.21 (installed like `sqlx-cli`, not a
  crate dependency). Stable releases, not the 0.9 release candidates.
- **Skeleton scope:** the crate, its build and dev loop, placeholder design tokens
  (light/dark), one page that shows the api is reachable, and CI. No screens until the
  designs arrive.

## Design (skeleton)

- `crates/web/`: `index.html` (trunk's entry), `Trunk.toml`, `src/main.rs` (mounts the
  app), `style/tokens.css` (CSS custom properties; light, dark by
  `prefers-color-scheme` and a `data-theme` override).
- **Dev:** `just web-dev` runs `trunk serve` on http://localhost:3000 and proxies
  `/api/` to the kind api (http://localhost:18082, from `just kind-api`), so the
  browser sees one origin, as in production.
- **Toolchain:** `rust-toolchain.toml` gains the `wasm32-unknown-unknown` target.
- **CI:** clippy and a build of `pedagog-web` for `wasm32-unknown-unknown` (the
  workspace's native build already compiles it).

## Alternatives considered

- **SSR inside the api:** first paint without WASM and direct use of the store and
  permissions, but a heavier api build (`cargo-leptos`) and hydration complexity.
- **SSR as a separate service:** independent deploys, but three hops and no reuse.
- **Server-rendered HTML + htmx:** simplest, but departs from Leptos and puts UI in
  the api.

## Open questions

- **Serving in the cluster:** the api serving the static files (`tower-http`'s
  `ServeDir`, a new dependency) vs a small static-file container behind Traefik
  (`/` → web, `/api` → api). Decide with the `/api` move.
- **Wasm tests:** `wasm-bindgen-test` (new dependency) for browser-only logic, or keep
  logic in plain functions tested natively.
- **Bundle size budget** (e.g. under 1 MB compressed) and `wasm-opt` level.

## Rollback

The skeleton is additive: delete `crates/web/`'s new files, the toolchain target, the
`just` recipes and the CI steps.

## Implementation steps

1. `chore(web)`: skeleton (crate, tokens, api-reachable page, `Trunk.toml`), toolchain
   target, `just web-dev` / `web-build`, CI steps, SETUP (local dev) and ARCHITECTURE
   (Frontend).
2. Later, with the designs: the api under `/api` (and hammer), serving in the cluster,
   the router, the app shell, and screens in the brief's order.

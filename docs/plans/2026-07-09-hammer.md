# Plan: hammer — Build Tool

## Rationale

The image build pipeline needs a first-class tool to:
- Define and inspect build recipes for toolchains and platforms
- Translate recipes into an ordered, inspectable list of build steps
- Drive in-cluster image builds via Kaniko
- Keep default recipes immutable and versioned alongside the binary

A shell script approach lacks inspectability and type safety. A general-purpose build tool
(Dockerfile only, Ansible, etc.) doesn't map cleanly to our recipe model. `hammer` is a
thin, purpose-built CLI that owns this one job.

## Alternatives Considered

- **Shell scripts**: simple but not inspectable or composable; recipe errors surface at
  runtime, not at plan time.
- **Ansible**: heavy dependency, YAML playbooks not ergonomic for this domain, no native
  Kaniko integration.
- **Dockerfile generation only**: doesn't address recipe resolution, addon dependency
  chaining, or the `hammer plan` inspection workflow.

## Future Recipe Features (deferred)

- **Multi-stage builds** — the recipe format needs to express multi-stage builds for
  cases where an artifact must be compiled in one stage and copied into the final image
  (e.g. the daemon binary, or building a toolchain from source). Rough shape:
  ```yaml
  stages:
    - name: builder
      image: rust:1.79
      steps:
        - name: Compile daemon
          run:
            - cargo build --release --bin daemon
  steps:
    - name: Copy daemon
      copy_from:
        stage: builder
        src: /target/release/daemon
        dst: /usr/local/bin/daemon
  ```
  Containerfile generation must handle `COPY --from=<stage>` accordingly. Design TBD.

- **Build time optimization** — extension VSIXs fetched from Open-VSX at image build time
  are slow (large binaries, network-dependent). Future: hammer pre-fetches VSIXs and
  `COPY`s them in rather than running `code-server --install-extension` during the build.
  Also: pin code-server version and download the `.deb` directly instead of using the
  install script, so the URL is stable and layer caching is tight.

- **Multi-OS recipes** — the `os` field in toolchain and platform recipes should accept
  a single id, a list, or a wildcard:
  ```yaml
  os: ubuntu-22          # single
  os: [ubuntu-22, ubuntu-24]  # explicit list
  os: "*"                # all known OSes
  ```
  The resolver uses this to match recipes against the OS being built. Design TBD.

- **First-class env vars and file writes** — recipes should be able to set environment
  variables and write files as explicit step actions (not just `run:` shell commands).
  Env vars set this way should be usable for string interpolation within subsequent steps
  and for conditionally including packages or run commands. Design TBD.

- **Recipes in a separate repo** — all default recipes (`os/`, `toolchains/`,
  `platforms/`) will live in a dedicated repo, added to the platform repo as a git
  submodule. This allows recipes to be maintained, tested, and versioned independently
  from the platform. The submodule path within the repo is TBD.

## Open Questions

- What additional fields does the OS YAML need beyond `id`, `upstream`, `image`,
  `pkg_manager`? (setup scripts, permission configuration — deferred)
- How does hammer authenticate to the cluster registry when pushing? (service account /
  imagePullSecret — deferred to Kaniko integration step)
- Should `hammer plan` output a Containerfile, a YAML plan, or both?
- How does version resolution work when `version:` is omitted on an addon reference?
  (error if multiple versions exist, use the sole file if only one)
- Should the Kaniko job timeout be configurable per OS / toolchain?

## Rollback Plan

`hammer` is a standalone binary with no runtime side-effects until `hammer build` or
`hammer build-os` is invoked. Rolling back means reverting the crate and recipe files.
Kaniko jobs are ephemeral k8s Jobs — failed or cancelled builds leave no persistent state
beyond a partial push to the registry (which is harmless; the tag is not promoted until
the build succeeds).

## Recipe Format

### OS Definition (`os/<id>.yaml`)

```yaml
id: ubuntu-22
upstream: ubuntu:22.04        # base image pulled from Docker Hub for os builds
image: pedagog/ubuntu:22      # tag pushed to cluster registry after build
pkg_manager: apt              # apt | apk | dnf
```

`hammer` hardcodes the invocation per `pkg_manager`:
- `apt` → `apt-get install -y`
- `apk` → `apk add --no-cache`
- `dnf` → `dnf install -y`

More fields TBD when OS-level setup scripts and permission config are designed.

### Toolchain (`toolchains/<os-id>/<id>/<version>.yaml`)

```yaml
id: gcc
version: "13"
os: ubuntu-22
steps:
  - name: Install gcc 13
    packages:
      - gcc-13
      - g++-13
  - name: Set as default compiler
    run:
      - update-alternatives --install /usr/bin/gcc gcc /usr/bin/gcc-13 100
addons:
  - gdb:14
  - valgrind:3
```

- `id` + `version` together identify a toolchain uniquely.
- `os` ties the recipe to a specific OS definition; a toolchain may exist under multiple OS directories.
- `steps` is an ordered list; each step has `packages`, `run`, or both.
- `addons` references other toolchain IDs with optional version (`id:version`). Resolved
  using the same search paths as direct toolchains.
- Addon resolution: if version is omitted and exactly one version file exists, use it;
  if multiple exist, error and ask the user to be explicit.

### Platform (`platforms/<os-id>/<id>.yaml`)

```yaml
id: interactive
os: ubuntu-22
steps:
  - name: Install code-server
    run:
      - curl -fsSL https://code-server.dev/install.sh | sh
  - name: Configure code-server
    run:
      - ...
```

- Platforms define how the system interacts with pods (interactive session, submission
  runner, etc.). Custom platforms are not supported — the set is defined by Pedagog.
- Current platforms: `interactive`, `submission`, `multi-submission`.
- Platform recipes install and configure the components that the platform layer needs
  (e.g. code-server for `interactive`).

### Platform (`platforms/<os-id>/<id>.yaml`) — Interactive specifics

The `interactive` platform recipe installs code-server, writes a base `policy.json`
(without `AllowedExtensions` — that is merged in by hammer at build time from
`assignment.yml`), and removes built-in extensions that are not permitted in exam
environments:

```yaml
id: interactive
os: ubuntu-22
steps:
  - name: Install code-server
    run:
      - curl -fsSL https://code-server.dev/install.sh | sh
  - name: Write base policy.json
    run:
      - mkdir -p /etc/vscode
      - ...   # writes policy.json without AllowedExtensions
  - name: Remove unwanted built-in extensions
    run:
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/tunnel-forwarding
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/simple-browser
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/github
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/github-authentication
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/copilot
      - rm -rf /usr/lib/code-server/lib/vscode/extensions/terminal-suggest
```

`AllowedExtensions` is not part of the platform recipe — hammer generates it at build
time as the union of `extensions.install` and `extensions.allow` from `assignment.yml`
and merges it into the policy.json written by the platform step.

### Addon Resolution Order

hammer searches for toolchain/addon recipes in this order:
1. Instructor-specified additional paths (from `assignment.yml` `toolchain_paths:`)
2. `/etc/hammer/toolchains/` (extracted defaults — read-only)

Default recipes are embedded in the binary and extracted to `/etc/hammer/` before any
build. The extracted defaults are read-only; instructors cannot modify them.

## Subcommands

| Command | Description |
| --- | --- |
| `hammer plan <assignment.yml>` | Resolve recipes and print the ordered build plan (steps, packages, run commands) without building |
| `hammer build <assignment.yml>` | Submit a Kaniko job to build the instructor image for this assignment |
| `hammer build-os <os-id>` | Submit a Kaniko job to build (or rebuild) a pedagog OS base image |

`hammer plan` is the primary inspection tool — instructors and operators can verify what
will be installed before committing to a build.

---

## Kaniko Integration

- hammer generates a Containerfile in memory from the resolved step list.
- The Containerfile uses `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}` so the registry address
  is injected at build time, not baked into recipes.
- hammer submits a Kubernetes Job using the Kaniko executor image.
- The registry address is read from hammer's config/environment (not from recipe files).
- The built image is pushed to `<registry>/<image>:<tag>` on success.

## Implementation Steps

1. **Scaffold `crates/hammer/`** — add to Cargo workspace; `clap` for subcommands; `serde`
   + `serde_yaml` for recipe parsing. Stub all modules. ✓
2. **Test image** — `images/code-server-test/` — a standalone Containerfile that directly
   implements the code-server lockdown (policy.json, extension removal, nologin shell,
   extension pre-install). Run and verify all assumptions before baking them into recipes.
   See verification checklist in that directory.
3. **Write default OS YAML** — `os/ubuntu-22.yaml`.
4. **Write default toolchain YAMLs** — gcc/13, gcc/12, gdb/14, valgrind/3, python/3.12,
   rust/1.79, nodejs/22 for ubuntu-22. (Inform recipe content from test image findings.)
5. **Write default platform YAMLs** — interactive, submission, multi-submission for ubuntu-22.
6. **Define serde types** — `OsDef`, `ToolchainRecipe`, `PlatformRecipe`, `Step` in
   `recipe.rs`.
7. **Implement resolver** — `resolve.rs`: load OS def, resolve toolchain + addons
   (recursively, cycle detection), merge into ordered step list.
8. **Implement `hammer plan`** — print resolved step list to stdout in human-readable form.
9. **Implement Containerfile generation** — `plan.rs`: step list → valid Containerfile text.
10. **Embed defaults** — use `include_dir` or `build.rs` to embed `toolchains/`,
    `platforms/`, `os/` into the binary; extract to `/etc/hammer/` at startup if absent.
11. **Implement `hammer build` and `hammer build-os`** — `build.rs`: Containerfile →
    Kaniko k8s Job spec → submit via k8s API.
